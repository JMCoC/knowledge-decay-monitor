# S1-04 Processing Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Task 0 is a spike and runs native (no commits); Tasks 1–7 are TDD with atomic commits.

**Goal:** Process a confirmed v1 (`uploaded + upload_state='confirmed'`) through a server-side pipeline — parse → deterministic chunk (450/50) → `gte-small` embeddings (384d) → atomic persist — ending in `ready + active + active_version_id` or `processing_failed`, with no manual work and no LLM calls.

**Architecture:** `finalizeUpload` conditionally schedules a `Route Handler` via `after()`; the handler owns auth (internal token) and the CAS claim (`uploaded + confirmed → processing + operation_id + started_at`, 180 s lease, no sweeper); `runProcessing(versionId, operationId)` downloads the canonical object via `downloadStorageObject`, parses/chunks/embeds, and closes with the single `finish_processing` RPC transaction (`INSERT chunks + ready/active + pointer`). The persisted state (`uploaded + confirmed`) is the queue — no queue table, no cron, no Edge Functions in S1-04.

**Tech Stack:** Next.js 16.3.5 (App Router, `after()`, Route Handlers), TypeScript strict, Zod 4.6.5, `@supabase/supabase-js` 2.117.2 + `@supabase/ssr` 0.12.7, PostgreSQL + pgvector (`extensions.vector(384)`) with pgTAP via Supabase CLI, Vitest 5.0.2, `@sentry/nextjs` 10 (already present), `unpdf` + `mammoth` (dynamic import, new), Markdown own mini-parser, embeddings via Task 0 verdict (`supabase.ai.Session` / HF Inference `supabase/gte-small` / `@xenova/transformers`).

**Spec:** [`docs/superpowers/specs/2026-10-06-s1-04-processing-spec.md`](../specs/2026-10-06-s1-04-processing-spec.md) — read it before Task 1. Task 0 writes its verdict into spec §2 before anything else proceeds. The spec is the source of truth; this plan argues from it.

Batch 1–10 files already enforced in S1-02; S1-04 processes one version per worker invocation. Internal worker timeout is below the platform timeout (provisional ~50 s, frozen in Task 0) and maps to `processing_failed`. CAS lease is 180 s in `processing_started_at` with no sweeper in S1-04. **Service role is server-only.** Every DB/Storage call in the pipeline uses `createServiceClient()` on the server. Never expose `SUPABASE_SERVICE_ROLE_KEY`, `INGESTION_INTERNAL_TOKEN`, paths, hashes, or bytes to the browser. Reads of `document_versions` in the worker use `service_role`, never user-scoped RPCs like `get_confirmed_document_path(p_user_id, …)`.

**Never process legacy.** CAS and RPC admit only `uploaded + confirmed`. Seed rows (`ready + active + synthetic vectors`) and `upload_state IS NULL` rows are never touched.

**Sentry discipline.** Only `captureOperationFailure({ module: "ingestion", operation: "process", code })` with codes from `src/lib/observability/safe-event.ts`: `PROCESSING_FAILED`, `PARSING_FAILED`, `CHUNKING_FAILED`, `EMBEDDING_FAILED`, `PERSISTENCE_FAILED`. There is no `EMBEDDING_UNAVAILABLE` code — map that case to `EMBEDDING_FAILED`.

**Imports.** Use the `@/*` alias (`./src/*`). Between modules import only another module's `index.ts` and `@/types/*`. The Route Handler and `processing.ts` are server-only (`server-only`, no client barrel leaking parsers/worker). No `Buffer` in isomorphic code paths; worker-only Node APIs stay in the handler/worker files with dynamic imports for `unpdf`/`mammoth`.

**Do not touch.** `src/modules/ingestion/upload-store.ts`, `verification.ts`, `storage.ts` are read-only (import, don't modify). ## Review Focus

Seven inputs and failure modes the spec implies that no task's tests would otherwise catch. Each has a test pinned to the task that owns the code.

1. **A double `finalizeUpload` schedules two workers.** The second `after()` is wasted work even though the CAS would serialize it. → Task 6: `confirmed + uploaded` schedules once; `processing/failed/ready/legacy` never schedules; snapshot intact.
2. **A CAS that finds nothing still invokes the worker.** An empty `RETURNING` (already `processing`, or `upload_state != 'confirmed'`) must be a 204 with no `runProcessing` call. → Task 4: empty-CAS tests for both reasons, asserting `runProcessing` was not called.
3. **An empty PDF becomes `ready`.** `unpdf` returning `""`/whitespace (scanned, OCR-needed) must be `ParseError("NO_TEXT")` → `processing_failed`, never `ready`. → Task 2 (unit) and Task 5 (worker mapping).
4. **A stale worker overwrites a fresh claim.** `finish_processing` with an `operation_id` different from the persisted one must reject, so an old worker cannot activate over a new claim. → Task 1, pgTAP `throws_ok ... 22023`.
5. **The internal token leaks or is skipped.** Missing/wrong token must be 401 with no processing and nothing secret in the response; correct token passes via `timingSafeEqual`. → Task 4.
6. **A bad vector persists.** `NaN`/`Inf` or dims ≠ 384 must be `EMBEDDING_FAILED` → `processing_failed`, never an `INSERT`. The exact pgvector rejection code is confirmed in Task 0 and asserted in pgTAP. → Task 3 (unit) and Task 1 (pgTAP note).
7. **A crash between CAS and RPC looks like success.** The version stays in `processing` with `operation_id` set and no chunks. S1-04 declares this as known limit §10.3 (no test, no sweeper); S1-07 rescues it. → Documented, not tested — any test claiming to cover it in S1-04 fails review.
