# S2-08a Analysis Finalization — Transaccional Base Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Task 8a-0 is a native baseline/coordination gate (no commit) and must pass before Task 8a-1. Tasks 8a-1..8a-5 are strict TDD. Do NOT start any task until the user approves this plan.

**Goal:** Land the additive transactional base for S2-08 — two private staging tables, a deterministic finding fingerprint, the atomic `persist_analysis_batch` RPC and the atomic `finalize_analysis_success` RPC — plus the real (non-throwing) `createBatchPersistence(client)` / `createFinalization(client)` factories and their unit + worker-integration coverage, without changing any contract or the Edge gate.

**Architecture:** Staging lives in `private.analysis_finding_staging` / `private.analysis_finding_evidence_staging` (RLS on, no grants, keys by `(analysis_id, fingerprint)`), written only through the `service_role`-executable `public.persist_analysis_batch`. Success closes through `public.finalize_analysis_success` (11 ordered steps, `Consumed` + `analysis_completed` + `analysis_status`). The worker never sends a fingerprint: SQL recomputes it from normalized staging evidence using `private.canonical_jsonb`. A Deno-safe `fingerprint.ts` mirrors the same canonicalization for byte-identical parity tests. The seam factories stop throwing and use the injected client. This slice is additive: `private.finalize_failed_analysis`, the claim/fail/create_analysis_run locks, the `complete_analysis` revocation, the 3-flag Edge gate and the integration migration to `Consumed`/`Released` are S2-08b.

**Tech Stack:** PostgreSQL 15 (Supabase) + pgTAP, Next.js App Router + TypeScript strict, Supabase Edge Functions (Deno), Vitest, pnpm 12.5.1.

**Spec:** [`docs/superpowers/specs/2026-10-21-s2-08-analysis-finalization-spec.md`](../specs/2026-10-21-s2-08-analysis-finalization-spec.md) — read §4, §5, §6, §10, §11 before Task 8a-1. The spec is closed (`32e86b9`); any behavior change requires re-approval. **S2-08b** (`docs/superpowers/specs/…` §7–§9) is out of scope here.

## Review Focus

Five failure modes this slice must pin, each with a test in the owning task.

1. **Double CAS in `persist_analysis_batch`.** Reusing `yield_analysis_batch` / `renew_analysis_lease` (both re-CAS `expected_processed_pairs`, `supabase/migrations/20261017205245_s2_05_worker_handoff.sql:340-347`) would fail after step 3 already validated. The RPC must replicate the status/lease update inline (spec §5.3 step 6). → Task 8a-3: a worker-level spy proves neither legacy RPC is invoked during a real persist, and the staging + checkpoint commit together.
2. **Fingerprint SQL ↔ TS parity.** `persist_analysis_batch` recomputes the fingerprint in SQL; `fingerprint.ts` must produce the **byte-identical** value. → Task 8a-2 (TS algorithm + fixed vectors) and Task 8a-3 (SQL recompute equals the TS vector for the same input, 100 randomized fixtures).
3. **Cleanup trigger must not fire early.** The `AFTER UPDATE OF status` safety trigger (spec §5.4) must only wipe staging on terminal `completed`/`failed`, never during the `has_more=true` (`queued`) or `has_more=false` (`processing`) updates inside a persist. → Task 8a-1 (trigger predicate) and Task 8a-3 (staging survives a mid-scope persist).
4. **Cross-worker idempotency.** A repeated `finalize_analysis_success` with the **same** `operation_id` on an already-`completed` analysis returns early: no second `Consumed`, no second `analysis_completed`, no re-publish. → Task 8a-4.
5. **Zero findings vs reported-but-unstaged.** `staging_count = 0 AND reported > 0` → `P0001`; `staging_count = 0 AND reported = 0` → `completed` with `Consumed` + event; `staging_count < reported` (dedup) is **not** an error. → Task 8a-4.
